# Shared photo uploads and library selection

Every photo upload uses the tab-scoped queue in the root layout. An administrator scope under the admin layout binds jobs to the signed-in administrator. The same Media Library supplies the normal image, page cover, sharing cover, section background, Photo Grid, legacy Gallery and template photo pickers. JSON imports are unrelated and keep their own file control.

The input stays disabled until the client upload handler is ready. New uploads check for identical originals before transferring bytes and can reuse a verified existing photo, explicitly upload another copy or skip it. Files selected together with identical contents wait for the first copy to finish verification. See [duplicate choices, privacy and the new-uploads-only indexing boundary](photo-duplicates.md).

The queue runs at most two upload/processing jobs at once across all pickers and pages. It holds selected File objects in memory, sends original bytes to the existing signed private upload URL, then calls the existing completion endpoint. The server continues to verify administrators, validate files and generate stripped display copies/thumbnails. No database migrations, storage permissions, new billing services or browser-persistent photo copies are introduced.

Closing a picker, moving between admin screens, or following ordinary internal links keeps the root queue alive. The floating panel minimizes on navigation and completion, can be expanded, and lists active/failed jobs first with fifty visible entries at a time. Inside a photo picker, View upload progress opens the shared activity modal. Mounted library views refresh no more than once every two seconds as jobs finish; automatic refresh waits while a multiple-photo or management selection is active. Explicit Refresh library remains available.

Retrying failed transfers creates a fresh upload URL. An uncertain processing response retries completion against the same upload ID, which is idempotent on the server. Expired/missing pending uploads can be uploaded again. Queued jobs can be cancelled; failed jobs can be retried or removed. Successful/removed/cancelled jobs release File references. Signing out confirms unfinished work in the current tab, aborts its client requests and clears files. Account changes, authentication failures and the existing cross-tab sign-out signal also stop old jobs; late callbacks cannot restart them under another account. Already received photos may still finish processing on the server.

This queue is not durable across refresh, tab closure, browser termination or an OS kill. A browser unload warning is attached only while work or retryable files remain, but [beforeunload is not reliable on every mobile exit](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event). Keep the original tab open until completion. Other tabs have separate queues; they do not share File objects or provide a pre-sign-out inventory of another tab's uploads.

Media Library management allows direct photo selection, Select loaded, Clear and a permanent-deletion confirmation. Selections persist across loaded batches and filters. The floating bar counts selections outside currently loaded results; Review selection lets administrators find and remove these selections without deleting photos. The final deletion dialog also warns about not-shown selections. Known used photos are kept; every eligible deletion still passes the existing transactional server checks, including current contents/covers of private and trashed pages. History alone does not protect a photo. Deletion runs two requests at a time, retains failures for retry and removes successes from selection. Repeating an uncertain deletion is safe: an already-deleted photo returns not found and is considered finished. Editor pickers expose selection/use controls, not bulk deletion.

The dedicated Media Library remembers search, filters, grouping, filter-panel visibility, loaded batches and scroll in account-scoped tab storage for up to twelve hours. Returning reloads authorized metadata progressively, up to fifty saved batches, then restores the position. Refresh, changed filters and wheel/touch interaction cancel restoration; requests stop at an error or the end of results. Photo bytes and selections are never stored. Sign-out clears the preference entry, and unavailable browser storage falls back to ordinary browsing. Editor pickers do not restore the dedicated library's preferences.

Verification uses disposable local authentication, database and storage fixtures. Queue checks cover concurrency, queued cancellation, processing retry and account isolation. Browser journeys cover admin/public navigation, plain internal links, editor-picker handoff, reload warnings, sign-out confirmation, real upload/reuse, picker batching and bulk deletion with protected photos and partial failures. Real managed authentication and production access remain separate release checks.
